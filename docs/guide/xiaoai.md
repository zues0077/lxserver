# 小爱音箱投播

把 Web 播放器里的歌曲投送到小爱音箱播放（支持多台设备同时播放）。

> 该功能参考了 [songloft-plugin-miot](https://github.com/deerwan/songloft-plugin-miot)（MIoT 插件）、[miair-next](https://github.com/deerwan/miair-next)、[mijia-api](https://github.com/Do1e/mijia-api) 与 [songloft-player](https://github.com/deerwan/songloft-player)，在 lxserver 内用 TypeScript 原生重新实现，**不依赖 Python、无需额外镜像层**。

## 它是怎么工作的

```
浏览器（播放器）
   │ 1. POST /api/music/xiaoai/play  { songInfo, quality, deviceIds }
   ▼
lxserver
   │ 2. 用自定义源把歌解析成真实音频地址
   │ 3. 生成带签名、30 分钟有效的本地中转地址
   ▼
小爱音箱  ◀── 4. 通过 ubus(player_play_url / player_play_music) 下发地址，音箱自己去拉流

浏览器（自动续播守望）
   │ 5. 每 3 秒 GET /api/music/xiaoai/status 读音箱播放进度
   │ 6. 进度过半 → POST /api/music/xiaoai/prefetch 预解析下一首
   │ 7. 接近结尾 → 调播放器的「下一首」，回到第 1 步
   ▼
```

- 音箱只会照 URL 拉流，无法携带登录态，所以「谁能拉流」靠 URL 里的 HMAC 签名控制（`data/xiaoai.secret`）。
- 在线歌曲一律经 `/api/music/xiaoai/stream` 中转，回源时补上浏览器 UA 与 Referer，规避防盗链。
- 账号登录走米家云接口：`account.xiaomi.com` 取 `serviceToken`，`api2.mina.mi.com` 下发设备指令。

## 使用步骤

1. 打开 Web 播放器 → **设置** → **小爱音箱**。
2. 填写**服务地址**：必须是**音箱能访问到**的地址。
   - 局域网：`http://<NAS或服务器的局域网IP>:9527`
   - 建议值默认取**浏览器当前访问本服务的地址**（含真实端口），输入框下方点「用检测到的地址」即可填入
   - 容器部署时不要用网卡探测出来的地址：容器内网卡往往是 `10.201.x.x` 之类只存在于容器网络的地址，端口也是容器内端口（如 `9527`），音箱访问不到
   - 反向代理：填对外域名，例如 `https://lx.example.com`
   - 留空则按当前页面地址自动推断（仅在浏览器与音箱同一网段且地址一致时可用）
3. 登录小米账号：推荐「扫码登录」，用米家 App 扫码即可；也可用账号密码或 Cookie。
4. 点「刷新设备」，勾选要播放的音箱（可多选）。
5. 点「投送到小爱」：会把**当前歌曲立即投到音箱**，并把这个页面的播放目标切到小爱；此后点播放/切歌都会投送到音箱。切回本机点「切回本机播放」。
6. 想让**歌单自动连播**，保持「播放完自动下一首」处于开启状态（默认开启）。

## 触屏音箱的封面与歌词

带屏机型（如 `X08C`/`X08E`/`LX04` 等走 `player_play_music` 的型号）在投送时，服务端会按「歌名 + 歌手」去小米曲库搜索真实 `audioID`，音箱屏幕上就能显示对应封面与歌词：

- 歌名完全相等 + 歌手双向包含才算精确命中；未命中时按相关度取首条，再不行用默认封面
- 搜索结果按歌曲缓存 30 分钟，多台设备/重复投送不会重复请求曲库
- 可在设置里关闭「触屏显示封面歌词」；关闭后固定使用默认封面
- `audioID` 是超出 JS 安全整数范围的大整数，服务端在解析前先转成字符串，避免精度丢失导致封面错乱

## 自动续播（歌单连播）

音箱播完一首不会通知播放器，所以由播放器侧盯住音箱状态，到点自动接下一首。

**判定规则**

| 情况 | 行为 |
| --- | --- |
| 正常播放中 | 什么都不做，界面显示实时进度 |
| 距本首结束不足 45 秒 | 提前向服务端预解析下一首，切歌时直接命中缓存（**不依赖设备上报进度**） |
| 进入最后 25 秒 | 采样间隔从 3 秒加密到 1.5 秒，保证切歌点不被采样周期拖后 |
| 按真实时长算，还差 4 秒到结尾（实测延迟大时会自动加大） | **提前切歌**，让下一首在上一首收尾前接上 |
| 设备已停止且进度在末尾（≥97%） | 判定播完，切下一首 |
| **这一路流重新开始被拉第二遍** | 立即判定播完（最可靠的信号，见下方说明） |
| 设备不上报进度（老固件） | 用**真实时长 + 墙钟**预判，不再等「停止 6 秒」 |
| 音箱循环重拉时回报了小 `position` | 不拿它重锚计时，否则自动切歌会被无限推迟 |
| 你点了暂停 | 停止守望，点播放恢复后才继续续播；暂停时长不会计入已播 |
| 音箱被语音/米家 App 停在中途 | **不切歌**，继续等它恢复 |
| 长时间无人播放（4 分钟） | 停止守望，避免一直轮询云端 |
| 状态连续查询失败 | 累计 6 次后停止守望并提示 |

**为什么需要它**：投送模式下浏览器里其实没有在播放音频，播放器无法像本地播放那样感知「这首放完了」，必须靠主动查询音箱状态来判断。

**为什么时长要自己解析**：切歌时机完全取决于「这首歌到底多长」，而现成的两个来源都不可靠——
设备上报的 `duration` 取的是**云端曲目元数据**（走 `player_play_music` 的机型尤其如此，和推给它的音频往往不是一首），
歌曲列表里的 `interval` 来自音源搜索接口，实测偏差能到分钟级（214 秒的歌被标成 48 秒，于是放到 48 秒就切了）。
所以服务端在投送前顺带把音频文件头读一遍：MP3 用 Xing 帧数或「体积 ÷ 码率」，M4A 读 `mvhd`，FLAC 读 `STREAMINFO`，
把这个真实时长随 `/play`、`/prefetch` 响应下发，前端优先用它。局域网实测误差在 1 秒内。

**为什么要提前 4 秒 + 按实测延迟自适应**：音箱播完会立刻从头重拉同一个 URL，如果我们在它播完之后才决定切歌，
用户听到的就是「上一首重头播了几秒再跳」。提前量不能靠拍脑袋调大——[songloft#481](https://github.com/songloft-org/songloft/issues/481)
里用固定的负偏移去盖，盖小了不起作用、盖大了直接截掉结尾。

这里做的是**量出来再提前**：服务端知道「投送完成」和「音箱真的来拉这一路流」这两个时刻，
差值 `startDelayMs` 随 `/status` 下发；前端再加一次起播缓冲（2 × `startLatencyMs`）就是必须提前的量，
下限 4 秒、上限 10 秒。第一首只能猜，从第二首开始就按这台设备的真实速度校准。
时长本身也算准（见下），最后 25 秒把采样从 3 秒加密到 1.5 秒，切歌点就不会被采样周期拖后。

**加密采样为什么只到 1.5 秒**：每次查询都要经小米云往返，问得太密（0.8 秒）设备反而容易卡一下，
听感正是「突然静音一两秒」。提前量足够时，1.5 秒的粒度完全够用。

**为什么还要「流被重拉」这条**：时长再准也可能被音源转码差异带偏。音箱播完会自己重拉同一个 URL，
这件事服务端看得见——`/status` 会带回 `streamReplay`（这一路流已经完整拉过一遍、现在又开始新一轮）。
服务端在**新一轮请求建立连接的那一刻**就置位，不必等这一轮传完，所以比 `streamFull >= 2` 快几十秒。
前端看到就立刻切歌，不依赖设备上报的进度与时长。

**「重拉」必须连 Range 形式的续拉也算**：音箱续拉时带的是 `Range: bytes=xxx-`（起点不是 0）。
以前只认「从头拉」，于是音箱的续拉永远判不出来，前端收不到「播完」信号，
只能等墙钟——而墙钟要等整首的时长，**中间那段时间音箱一直在重放上一首**（听感就是「切歌时回放上一首的一部分」）。
现在的判据是「这一路流已经**完整送达**过（≥98%），音箱又来拉 = 它觉得歌放完了」，
不关心这次是从头拉还是续拉；反过来，整首还没送完时的中途续拉不算「播完」。
前端这边的守卫也从 5 秒压到 1 秒（信号已经足够准确，5 秒的等待等于让音箱白播 5 秒）。

**为什么歌会被「重拉」：长歌曾被服务端主动掐断**（已修）
早先的「上游读完了但音箱不读就放弃」逻辑，把「上游读完」当成了计时起点。
而本地缓存路径的上游是一段内存流、**瞬间就读完**，于是每一首都从 0 秒开始计时，
到第 180 秒连接被主动掐断——超过 3 分钟的歌**尾巴永远发不出去**，
音箱发现断了就重拉那一段，听感正是「切歌时回放上一首的一部分」。
现在改判「多久没能往连接写出数据」：音箱正常慢读时我们一直在写，不会误杀；
真的不听了，3 分钟后才放弃。日志里可见 `已发 10796601B / 总 10796601B`（完整送达）而不是停在某个固定字节数。

**重拉的数据先按住 4 秒**：如果一收到重拉就把音频喂给音箱，音箱会把这一段**再播一遍**。
所以服务端在重拉请求上先按住 4 秒，等前端确认并投送下一首——新的一首会把这路流作废（连接被掐断），
音箱就听不到这段回放（收尾时回 410）。期间前端没有投新歌（例如队列到头了）也只多等 4 秒，不会卡死。

**为什么设备位置回零时不能重锚**：走墙钟计时后，设备如果报了明显落后的 `position`，会用它重新校准起点（缓冲、状态没更新时有用）。
但音箱播完重拉时 `position` 会回到 0，这时候再校准等于把计时器推回整首开头，自动切歌就永远等不到了——
所以接近结尾、或设备位置回到开头时，一律不校准（songloft-plugin-miot 的 `canCalibrateAutoNextTimer` 也是这个结论）。

**与播放模式的关系**：切歌走播放器自身的「下一首」入口，所以随机、顺序、列表循环的行为与本地播放一致；
随机模式下会把预解析选中的那首「钉住」，确保解析的和播出的是同一首。
**单曲循环是个例外**：开了「播放完自动下一首」时按列表顺序强制推进一首，
否则 `playNext` 只会重播当前这首，自动续播等于没开。另外两次自动切歌之间至少间隔 2.5 秒，
防止投送是异步的、期间被重复判定连切好几首。

## 中转播放的流畅度

音箱播的是本服务中转出来的流，所以中转这一段的质量直接决定听感。这里有三个要点：

**1. 音源要尽快读进内存。** 音箱读流是「按播放节奏慢慢读」的：它自己的缓冲区一满就关 TCP 窗口。
如果直接把回源数据 `pipe` 下去，Node 默认只有 16KB 的水位，整首歌里会反复「暂停回源 → 缓冲见底 → 恢复回源」，
一首 4 分钟的歌能有上千次。每次恢复都要重新等音源的 TCP 窗口展开，音源随便抖一下就会原样传给音箱。
现在改成服务端自己的缓冲队列（最多 16MB）：多数歌曲几秒内就整首落地在内存里，之后音箱怎么慢读都与音源无关。
**这一条还有个副作用必须避开**：如果反过来让上游长时间挂着不动（比如等音箱慢慢读），
CDN 会把这个「空闲连接」判死断掉，表现就是下一首直接没声。所以读取和下发必须分开算。

**2. 写下游要按码率匀速喂。** 这是「突然静音一两秒」的根因。音箱的接收缓冲很小，
网络一股脑把整首灌给它，它来不及消费，中途就会出现「吃掉一段 → 静音 → 重连重拉」。
现在按 `总字节 ÷ 真实时长` 算出码率，以 **1.15 倍实时速度**均匀下发（相当于让它自己的缓冲缓慢上涨、始终有货），
并通过 `开始 3 秒的提前量` 保证起播不等。倍速不能调大：1.35 倍时仍然会让部分设备吃不完。
如果发现音箱快被饿着（缓冲见底），会自动把提前量 +2 秒，最多放宽到 20 秒——宁可多缓冲，也不能断。

**3. 不能让空闲超时把连接掐掉。** 缓冲写满后我们会主动暂停回源，暂停很容易超过 30 秒；
连接本身是好的，被空闲超时掐断就变成音箱侧断流。所以中转路径拿到响应后关掉 socket 空闲超时，
改用「60 秒一个字节都没有」来判断回源真的死了。

**4. 日志要能分清是谁慢。** 每次中转结束会打一行：

```
[XiaoAi] 中转完成 好妹妹乐队 - 归乡.mp3：已传 10961023B / 总 10961023B ｜首字节 120ms ｜上游读完 2.4s ｜下发完成 231.8s（平滑 3s）｜音箱侧最长停顿 8s
```

- `首字节`：音源多久才吐出第一个字节，大说明音源在拖起播速度；
- `上游读完`：把整首从音源拉进内存用了多久。这个值**总是很小**才是健康的，大说明音源慢；
- `下发完成`：交给音箱用了多久，正常情况下接近音频时长（音箱按实时速度读）；
- `平滑 Xs`：这次生效的提前量。出现 `放宽N次` 说明设备跟不上、已经自动加大缓冲；
- `音箱侧最长停顿`：只有在缓冲一直积压、连续 6 秒一点都没被消化时才会出现，
  出现即说明**卡顿发生在设备那一端**（音箱缓冲满、WiFi 抖动、或设备在忙别的），不是服务端没给数据。

> 早前的日志只打一个 `用时`，而上游 0.7 秒就把整首读进内存了，于是每天都是「用时 0s」，
> 把真正该看的「下发完成」彻底盖住——两个时间必须分开记。

## 投送前的音源校验

音源脚本只要拼出一个 URL 就算「成功返回链接」，它不会验证这个地址是不是还活着。
把死链交给音箱，表现就是「播放遇到问题，请稍后再试」——而这类失败从服务端日志里往往只看到一句「成功返回链接」。

所以投送前会做三件事：

| 步骤 | 行为 |
| --- | --- |
| 本地缓存优先 | 命中已缓存文件时直接把本地文件推给音箱（签名 token 授权），首字节几乎为 0，音源挂了也不影响 |
| 地址探测 | 未命中缓存时，用 `Range: bytes=0-63` 取前 64 字节，校验 `content-type` **和** 音频魔数（ID3 / fLaC / OggS / ftyp / 帧同步字…）；HTML、JSON、空响应、4xx 一律判为不可播 |
| 自动换源 | 探测失败就换下一个音源重试（同平台最多 5 个候选），再不行降一档音质重试；全部失败时接口直接返回失败原因，不再投给音箱 |

### 先缓存再投送

设置里新增开关「先缓存再投送」（默认关闭，对应配置项 `cacheBeforePlay`）：

- **关闭（默认）**：探测通过后立即投送远端中转地址，音箱直接按地址拉流，投送最快。
- **开启**：先把整首下载到本地，再投送本地文件。首次投送会多等几秒（一首 320k 约 5 秒），之后同一首歌直接命中缓存、秒开；网络较差或音源不稳时更不容易断流。

> 播放器本地播放时也会触发同一个缓存任务，服务端会先等它下完再判断，避免两边抢同一个 `.tmp` 文件。

## 播放控制的机型差异

| 场景 | 服务端处理 |
| --- | --- |
| 暂停 | 下发 `pause` 后连续回读设备状态；仍在上报播放说明该机型「受理但不执行」，自动升级为 `stop` |
| 触屏机型（`player_play_music`） | 暂停直接下发 `stop`（这类机型 pause 后状态机不更新） |
| 恢复播放 | 真暂停 → 下发 `play` 原位续播；若暂停已降级为 `stop`（媒体上下文丢失），前端会**重新投送这首**并提示 |
| 停止 | 先 `pause` 再 `stop`（部分型号单独 `stop` 不生效） |
| 切歌 | 由播放器的「下一首」触发重新投送，不依赖音箱的 `next`（部分固件不支持） |

**限制**

- **播放器页面必须保持打开**：守望跑在浏览器里（心跳放在 Web Worker，避免切到后台标签后被节流）。关掉页面后，音箱会把当前这首放完，但不会自动接下一首。
- 多台音箱同时播放时，以**勾选的第一台**作为进度来源。

| POST | `/api/music/xiaoai/login/captcha` | 提交图形验证码 |
| POST | `/api/music/xiaoai/login/verify` | 提交短信 / 邮箱验证码 |
| POST | `/api/music/xiaoai/login/cookie` | 用 `userId` + `passToken` 登录 |
| POST | `/api/music/xiaoai/logout` | 退出登录并清除本地凭据 |
| GET | `/api/music/xiaoai/devices?refresh=1` | 拉取设备列表 |
| POST | `/api/music/xiaoai/play` | 投送歌曲（可带 `deviceIds` 覆盖）；返回 `audioDurationMs` = 服务端解析出的**真实音频时长** |
| POST | `/api/music/xiaoai/prefetch` | 预解析下一首的播放地址（自动续播用，结果缓存 10 分钟），同样返回 `audioDurationMs` |
| POST | `/api/music/xiaoai/pause` / `resume` / `stop` / `next` / `prev` | 播放控制；`pause` 的 `results[].state` 为 `paused`（正常暂停）或 `stopped`（该机型降级为停止） |
| POST | `/api/music/xiaoai/volume` | 设置音量（0-100） |
| GET | `/api/music/xiaoai/status?deviceId=` | 查询播放状态：`playing` / `paused` / `status` / `volume` / `durationMs` / `positionMs` / `progressRatio`（时长已统一为毫秒）；另有 `streamFull`（这一路流被完整拉了几遍）与 `streamReplay`（拉过一遍后又开始新一轮＝已播完） |
| GET | `/api/music/xiaoai/stream?token=` | 音频中转地址（由签名 token 授权，无需登录态） |

除 `stream` 外，其余接口需要管理员口令（`x-frontend-auth`）或已通过认证的播放器会话。

## 配置文件

写在数据目录（容器内 `/server/data`）下：

- `xiaoai.config.json`：开关、服务地址、选中设备、设备列表等
- `xiaoai.token.json`：登录态（`passToken` + `serviceToken`），**权限 600，不包含密码**
- `xiaoai.secret`：流地址签名密钥，删除后已下发的播放链接立即失效

登录成功后只持久化 `passToken`，`serviceToken` 过期时会自动静默续期（约 12 小时一次）。

## 常见问题

**音箱提示"播放遇到问题，请稍后再试"**

按顺序排查：

1. **服务地址**（最常见问题）。必须是音箱能访问到、且端口正确的地址。容器内不要填 `127.0.0.1`，也不要用容器网卡探测出来的内网地址。
   自检：在手机浏览器打开 `http://<服务地址>/api/music/xiaoai/config`，能返回 JSON 才说明音箱也访问得到。
2. **中继能不能取到音频**。投送接口返回的 `streamUrl` 可以直接在浏览器里打开：
   - 返回 `audio/mpeg` 且能下载 = 中继正常，问题在音箱侧（型号白名单、音量、网络）；
   - 返回 `{"success":false,"message":"回源失败: ..."}` = 音源那边取流失败，消息里会带上音源的真实报错（如 `HTTP 403`、`回源返回的不是音频`）。
3. 部分型号（`LX04`/`L05B`/`X08A` 等）必须走 `player_play_music`，服务端已内置型号白名单；若某个型号出现「灯亮但无声」，可在配置里把该型号加入 `disabledModels` 强制改走 `player_play_url`。

> 回源已自动跟随 3xx 跳转：多数音源接口本身就是个跳转器（例如 `kw.php` 直接 302 到酷我 CDN），不跟随会拿到空响应，表现为音箱报「播放遇到问题」。
>
> 另外投送前会对候选地址做一次音频探测（见上文「投送前的音源校验」），死链会被自动剔除并换源；
> 如果所有音源都失败，接口会直接返回类似 `没有可用音源（已自动换源）：xxx: 地址不可播（HTTP 404）` 的消息，不会再出现「音箱收到指令但不出声」。

**自动下一首时衔接不够流畅（上一首重头播一两秒才跳）**

这是音箱的行为决定的：它播完一首会**自己重拉同一个 URL 从头再播**，所以「发现播完」到「新歌开声」之间的时间就是能听到的空档。
本项目在四处压缩它：真实时长（提前 4 秒、并按实测延迟自适应）、尾部 1.5 秒加密采样、投送地址用预解析缓存、以及服务端在看到第二轮拉流时立即下发 `streamReplay`。
如果仍然偏慢，先看 `/status` 的返回值：

- `streamReplay` 一直是 `false`、`streamFull` 也涨不上去：音箱没走我们的中转（可能回退到云端音源），检查投送地址里的服务地址是否可访问；
- 日志里投送来源是「音源 xxx」而不是「预解析地址」：预取没命中，看是不是每首歌都在 45 秒内就播完了（预取来不及）。

**账号密码登录返回"需要二次验证"**

小米对新设备登录有风控。优先使用**扫码登录**；或在浏览器登录小米账号后，从 Cookie 里取 `userId` 与 `passToken` 用 Cookie 方式登录。

**点了暂停但音箱还在放**

部分机型会「受理」暂停指令但音频继续播。服务端已自动处理：pause 后回读状态，仍在上报播放就升级为 `stop`，界面会提示「该机型不支持暂停，已停止播放」；这时点播放是**重新投送这首**，不是原位续播。

**触屏音箱不显示封面/歌词**

1. 确认设置里的「触屏显示封面歌词」是开启状态；
2. 只有走 `player_play_music` 的带屏机型才显示，`player_play_url` 机型没有这个能力；
3. 曲库搜不到时用默认封面，同名不同歌手的翻唱可能匹配到错误封面（可在配置里关闭该功能）。

**播放完不会自动播下一首**

请确认：
1. 设置里的「播放完自动下一首」是开启状态；
2. 播放器页面保持打开（自动续播由页面驱动）；
3. 从「播放目标」投送后再开始播放歌单，而不是只在本机播。

若界面提示「音箱没有开始播放」或「无法读取音箱状态」，说明音箱状态查询不通，通常是登录态过期或设备离线，重新扫码登录并刷新设备即可。

**多人使用**

小爱配置是服务级（全局）的：登录一个小米账号、共享一份设备列表。切换播放目标后，所有使用该播放器的用户都会投送到同一批音箱。
