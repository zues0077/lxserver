# 自定义音源自检护栏

> 一句话：让「音源脚本加载成功、但在后台静默空转吃 CPU」这类问题，从「只能靠二分法猜」变成日志和 `/health` 里一眼可见。

## 为什么需要它

自定义音源脚本是第三方 JS，服务端只负责把它们装进沙箱跑起来。一旦某个脚本有问题，往往表现为：

- **加载成功**，日志里一切正常（没有报错、没有超时）
- 但进程 CPU 长期被吃掉一大块、内存只涨不降
- 删掉某个音源后恢复正常，可你并不知道是哪一个

一个真实案例（实测数据，同镜像、同一批音源）：

| 配置 | 空闲 CPU | 内存 |
| --- | --- | --- |
| 0 个音源 | 0.00% | 45.7 MB |
| 12 个干净音源 | 0.00% | 55.2 MB |
| **仅加载某个混淆脚本** | **65.83%** | **270.7 MB** |
| 45 个音源（剔除它） | 0.00% | 85.9 MB |
| 44 个音源（含它） | 59.87% | 512.8 MB |

结论很反直觉：**与音源数量完全无关，就是单个脚本在空转**。

护栏就是为这类问题设计的。

## 三层防护

### 第一层：静态体检（加载前，零运行时开销）

读取脚本源码后、真正解析前做一次特征扫描，只看结构特征、不看业务代码。

**A 级（高危 → 自动隔离）**

| 特征码 | 含义 | 检测方式 |
| --- | --- | --- |
| `infinite_loop` | 空死循环 | `while(!![]){}` / `while(true){}` —— **空循环体** |
| `debugger_trap` | 反调试陷阱 | `debugger` 被塞进循环或定时器回调里 |
| `sandbox_escape` | 沙箱逃逸 | `Function("return this")` 之类取回宿主全局 |
| `busy_polling` | 忙轮询 | 多个间隔 ≤ 16ms 的 `setInterval` |

**B 级（可疑 → 只标记，不隔离）**

| 特征码 | 含义 |
| --- | --- |
| `obfuscated` | 命中 jsjiami / sojson / obfuscator 水印 |
| `hex_identifiers:NNN` | `_0x1a2b` 形式的混淆标识符 ≥ 300 个 |
| `string_array` | 混淆常见的字符串数组声明 |
| `while_true_loop` | 非空体的 `while(!![])` |
| `long_line` | 存在超长行（> 5000 字符），典型的压缩混淆产物 |
| `dynamic_eval` | 使用 `eval(` |
| `host_access` | 调用 `process.exit(` |
| `debugger_statement` | 出现 `debugger`（未构成陷阱） |

> **为什么混淆只标记不隔离**：市面上大量音源都由 jsjiami 之类的工具混淆，混淆本身不等于恶意。实测 46 个常见音源中有 12 个命中混淆特征，但它们全都正常工作 —— 如果按混淆特征隔离，会直接误伤四分之一的音源。
>
> 同理，`while(!![])` 在混淆模板里常用于「字符串解密自检」（形如 `while(!![]){try{...;break}catch(e){}}`，体内有 `break`），**只有空循环体才是真死循环**。这个判据是实测校准出来的。

### 第二层：运行期 CPU 采样（加载后）

- 每 2 秒采样一次主线程 CPU（`process.cpuUsage()`），维护 15 秒滑动窗口
- 只有**同时满足**以下条件才算异常：窗口均值超过阈值（默认 30%）、且期间没有音源加载/重载在进行、且**连续两个窗口**都超标
- 采样器只在启用护栏时运行，且 `unref()`，不影响进程退出

### 第三层：复检归因（定位到具体脚本）

检测到异常后，护栏会告诉你「是谁」：

1. 候选排序：静态命中的 A 级优先，其次按混淆标识符数量排序（最多 6 个）
2. 逐个卸载单个候选脚本 → 等 3 秒让残留自旋退出 → 再测 3 秒窗口 CPU
3. CPU 明显回落（下降 ≥ 10 个百分点且 ≥ 基线的 40%）即认定为真凶
4. 未命中的候选**立即恢复加载**，不影响其他音源

> 定位到第一个真凶后即停止本轮复检 —— 因为真凶一被卸载，最初的基线就失效了，继续测后面的候选会把它们全部误判为「也下降了」。若还有其他热点，下一轮采样会重新触发。复检结束有 10 分钟冷却，避免反复重载音源。

## 命中后会发生什么

| 情况 | 动作 |
| --- | --- |
| A 级静态命中（`isolate` 模式） | **隔离**：跳过加载 + 写隔离记录 + 日志告警 |
| A 级静态命中（`warn` 模式） | 只告警，照常加载 |
| B 级命中 | 日志标记 + 记入 `/health` 的 `flagged`，照常加载 |
| 复检确认热点（`isolate` 模式） | **隔离**该脚本 |
| 复检确认热点（`warn` 模式） | 只告警并提示手动禁用 |

**隔离的语义**

- 隔离 = **本次运行跳过加载该脚本**，不会删除文件、不会改写 `sources.json` 里的启用开关
- 隔离记录写入数据目录的 `source-guard.json`，重启后依然生效
- 记录以脚本内容的 sha256 指纹为键：**脚本一更新（指纹变化）隔离自动解除**，无需手动清理
- 彻底关闭：设 `SOURCE_GUARD_ENABLED=false` 重启，或把 `source-guard.json` 里的条目删掉

## 配置项

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `SOURCE_GUARD_ENABLED` | `true` | 总开关 |
| `SOURCE_GUARD_MODE` | `isolate` | `isolate` = 告警 + 自动隔离；`warn` = 只告警（观察期推荐先用这个） |
| `SOURCE_GUARD_CPU_THRESHOLD_PERCENT` | `30` | 空闲 CPU 异常阈值（单核百分比） |
| `SOURCE_GUARD_SAMPLE_INTERVAL_MS` | `2000` | 采样间隔 |
| `SOURCE_GUARD_WINDOW_MS` | `15000` | 判定窗口长度 |
| `SOURCE_GUARD_PROBE_ENABLED` | `true` | 是否启用复检归因 |
| `SOURCE_GUARD_PROBE_WINDOW_MS` | `3000` | 单候选复检的测量窗口 |
| `SOURCE_GUARD_PROBE_MAX_SCRIPTS` | `6` | 单轮最多复检多少个候选 |

## 出现误报怎么办

护栏的判定刻意偏保守（宁可不隔离也不误伤），但仍然可能遇到：

1. **先切到观察模式**：设 `SOURCE_GUARD_MODE=warn` 重启，此时只告警、不隔离，可以对照日志确认是否真的有问题
2. **确认是误报**：删掉 `source-guard.json` 里对应的条目（或整个文件）重启即可恢复
3. **脚本更新后自动恢复**：即使不手动处理，只要你更新了该脚本文件，指纹变化就会让隔离自动解除
4. **CPU 异常但复检没定位到**：说明负载可能来自宿主自身（如同步任务、下载、转码网络等待），日志会明确提示这一点，此时不会隔离任何脚本

## 它不会做什么

- 不做 vm2 沙箱加固，也不审计脚本的联网行为
- 不会因为「混淆」就禁用音源
- 不修改你的音源配置（`sources.json`）与脚本文件
